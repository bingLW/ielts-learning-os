## 1. 产品目标与定位

### 1.1 一句话定位

**v2.7 是「决策与排程层」**：把已存在的诊断、证据、材料、词汇、复测、预算六路数据，收敛成一条**可解释、可确认、可回滚**的学习路线。它不是聊天机器人，也不是让 LLM 直接排课的黑箱——时间与优先级由确定性规则裁决，AI 只负责解释、提议候选与找理由。

### 1.2 相对既有能力「新增」什么

| 既有能力 | 它已经解决了 | 它**没有**解决的（= v2.7 的新增价值） |
|---|---|---|
| v2.1 动态预算（`adaptivePlan.ts` / `replan.ts` / `getEffectiveBudget`） | 给定「今天有多少分钟」，产出今天做什么 | **不解释为什么是这些**；没有跨天视野（7/30/90）；重排无预览、无前后对比；无版本治理 |
| v2.2 证据链（`evidence.ts` / `retest.ts` / `weakness.ts`） | 记录 Baseline→Transfer 六段证据，按加权错误率排序弱项 | **不做裁决**：证据只产出「候选弱项」，谁该优先、谁该先补测、谁该让位给到期复习，无人回答 |
| v2.4.1 诊断（`profile.ts` / 诊断会话） | 给出四技能方向等级 + 置信度 + doNotInfer | 诊断结果**不转化为计划**；低置信度维度在计划里没有专门通道 |
| v2.6 材料（`taskProposal.ts` / `MaterialPack`） | 单份材料拆成不超过预算的任务草案 | **只在单材料内部生效**，无全局候选池竞争；材料任务与复习/复测/核心训练谁优先，无人裁决 |
| v2.4 AI Engine | 提供解释与内容生成能力 | AI 与排程**没有边界契约**；无「AI 建议超预算怎么办」的裁决条款 |

**新增的三件事**：
1. **裁决**：把「候选弱项」升级为「已证实缺口 / 待确认维度」两池，并给出 P0–P3 的可解释排序；
2. **视野**：7 天（启动）→ 30 天（阶段）→ 90 天（周期）三层计划，且三层按单向下依赖，上层变更不静默改写下层；
3. **治理**：每次生效落 `PlanVersion`，支持预览重排、前后对比、回滚、变更原因留痕；AI 的建议必须被调度器约束。

### 1.3 三条产品原则（可断言）

| # | 原则 | 可断言的表达 |
|---|---|---|
| G1 | **证据说话，置信度分层** | 低置信度维度**永不**进入「已证实缺口」排序，只进「待确认维度」并优先排补测/低风险练习；UI 上不存在「你最弱的是 X」这种基于 LOW 置信度的结论 |
| G2 | **规则排程，AI 只在框内说话** | 时间、优先级、复习日期、装箱 100% 由确定性纯函数决定；AI 输出经 schema 校验后**与调度结果比对**，超预算一律被拒；AI 不可用时 100% 功能可用（AC-17） |
| G3 | **用户的确认权不可绕过** | 任何改变已 `confirmed` 计划的动作，必须经过「预览 → 用户确认 → 新版本」；AI 与本系统都不得无提示重写 |

## 2. 用户故事

单一角色：**学习者本人（单用户本地应用，无账号体系）**。以下 12 条按使用时机排序。

| # | 故事 | 验收要点 |
|---|---|---|
| US-1 | 作为刚做完诊断的学习者，我希望系统给我一份**保守的第一周计划**，避免一上手就被安排到崩溃 | 7 天计划任务量 ≤ 当前预算的 85%；首周必含「确认基础问题」类任务；不出现 30 天阶段目标已被预设为"完成" |
| US-2 | 作为听力强、写作弱的学习者，我希望计划**不要把四项平均分配**，写作该多拿时间 | 技能配比按证据偏离均值；测试场景：四技能差异明显时，写作分钟占比显著高于基线配比（AC-4、AC-6） |
| US-3 | 作为只在周末有 4 小时、工作日只有 30 分钟的学习者，我希望系统按**周总量**分配，而不是每天固定同一张表 | 工作日/周末预算差异被尊重；周总量不超 WeeklyTarget（AC-3、AC-4） |
| US-4 | 作为学习者，我希望看到「为什么今天安排了这个」，并且能点进证据看原文/作答 | 每条任务可展开：推荐原因 / 对应目标 / 对应缺口或待确认维度 / 预计分钟 / 优先级 / 前置条件 / 预计产出 / 不做的影响 / 来源是「规则」还是「AI 建议」（AC-8） |
| US-5 | 作为学习者，当系统说我某个子技能弱时，我希望它**先给我看证据够不够**，而不是拿一次错题给我定性 | 低置信度维度显示为「待确认，需 N 次样本」，只排补测；已证实缺口与待确认维度分区展示（AC-6） |
| US-6 | 作为学习者，我某天只有 15 分钟，我希望系统只给我「维持记忆」的最小动作，并且**不要把这一天算作失败** | 15 分钟只排到期复习/极少量维护项；不生成完整学习日；休息日与应急日不产生 MISSED（AC-3、AC-11） |
| US-7 | 作为学习者，我临时加班只能做 20 分钟，我希望**已经做完的保留**，剩下的重新安排，并且能先看到「重排后会变成什么样」再决定 | 重排前展示前/后对比（增减任务、分钟变化、被移走的任务及原因）；已完成任务不被改写；确认后才落库（AC-9、AC-10） |
| US-8 | 作为学习者，我不希望昨天没做完的 5 个任务全都堆到今天 | 过期任务按重要性/时效裁决：升格、降格、进 backlog 或放弃，每项有原因；单日滚存条数有上限（AC-11） |
| US-9 | 作为学习者，我希望每周有人告诉我「这周真正变好的是什么、还没解决的是什么、下周只改一件事」 | 周复盘输出 5 项固定内容；调整需达最小样本/趋势阈值，短期正确率波动不触发大改（AC-12） |
| US-10 | 作为学习者，我想知道 3 个月往哪走，但**不想被承诺"90 天升一个 CEFR 等级"** | 90 天分 Calibration / Build / Apply & Transfer 三阶段；1 个主突破主题 + 最多 2 个次要主题；界面明示「周期是管理单位，不保证等级提升」（AC-13） |
| US-11 | 作为学习者，当系统建议我进入下一阶段时，我要看到**它凭哪些证据这么说**，并有权拒绝 | readiness 结论必须列出：关键能力证据、多材料一致性、无辅助完成、延迟保持、迁移情况、置信度覆盖；学习天数与单次 AI 分数不参与判定；最终由用户确认（AC-14） |
| US-12 | 作为学习者，我改错了计划想退回上一版，我也想知道一个月前我是怎么安排计划的 | 计划历史可列出每次版本（时间、变更来源、原因、预算、前后任务差异），可对比两个版本，可恢复到某版本（生成新版本，而非删除历史）（AC-15） |

## 4. UI 设计稿（文字版）

**信息层级总原则**：**决策层（Dashboard）→ 依据层（Evidence & Gap）→ 操作层（Builder / Preview）→ 记录层（History）**。任何「结论」都必须能一跳抵达「依据」。

**全局视觉约束**

| 项 | 规则 |
|---|---|
| 来源标记 | 每条任务/结论前有来源徽章：`规则`（灰）/ `AI 建议`（淡紫）/ `用户编辑`（蓝）—— 三态必须可见且不可合并 |
| 置信度 | 仅三档 `高/中/低`，低置信度统一用虚线边框 + 「待确认」文字，**不使用**「最弱/最差」等定性措辞 |
| 技能口径 | 四技能独立卡片；Grammar / Vocabulary / Sentence Structure 只出现在「辅助维度」折叠区，标注「辅助维度，不计入四技能配比」 |
| 数字口径 | 任何分钟数都标注是「计划分钟 / 实际净分钟」，二者不合并显示 |
| 空态 | 一律给「下一步可做什么」的具体按钮，不出现「暂无数据」死胡同 |

### 4.1 Adaptive Planner Dashboard（`/planner`）

| 项 | 内容 |
|---|---|
| **页面目的** | 一屏回答「我现在在哪、今天该干什么、系统想改什么、我需要确认什么」 |
| **信息架构** | ① **状态带**：当前阶段 / 90 天第 N 天 / 本周已投入 vs 目标 / 今日预算（tierCode + 分钟）<br>② **今日决策卡**：今日任务 N 条、总计划分钟 / 预算、优先级分布（P0/P1/P2/P3 各几条几分钟）、「查看今天计划 →」跳 `/plan`<br>③ **待你确认区**（置顶红点）：待确认的计划版本 / 待确认的重排预览 / 待确认的 readiness 建议 / 待确认的周权重建议，每条一行 + 「去确认」<br>④ **本周缺口条**：四技能各自的「目标占比 vs 实际占比 vs 缺口分钟」迷你条<br>⑤ **弱项/待确认双栏**：「已证实缺口」Top3（带证据数）+「待确认维度」Top3（带还差几次样本）<br>⑥ **系统提示**：画像过期 / 无基线技能 / 证据覆盖不足 等 banner |
| **关键交互** | 点击任一「待你确认」进入对应预览；点击缺口项跳 Evidence & Gap Summary 并定位到该维度；「重新生成本周计划」走 Builder 而非直接覆盖 |
| **空态** | 未完成诊断 → 只显示一张卡「先做一轮诊断，系统才有依据排计划」（按钮跳诊断），其余区隐藏 |
| **错误态** | 快照构建失败 → 顶部红条「无法读取学习数据（原因）」，仍可查看上一版计划（只读），禁止生成新计划 |

### 4.2 Evidence & Gap Summary（`/planner/evidence`）

| 项 | 内容 |
|---|---|
| **页面目的** | 让用户看清「系统凭什么说你这里弱 / 凭什么说还不知道」 |
| **信息架构** | ① **四技能分栏**（Listening / Reading / Speaking / Writing 独立 Tab，不合并成一个总分）<br>② 每个 Tab 内两块：<br>　**A. 已证实缺口**：子维度 / 方向估计（标「AI 辅助估计」）/ 置信度 / 证据条数 / 最近 Baseline·Immediate·Delayed·Transfer 各几条 / 主要错误类型 / 重复频率 / 「查看证据」<br>　**B. 待确认维度**：子维度 / 当前置信度 / 还缺什么（样本数 or 无基线 or 画像过期）/ 建议补测方式 / 预计分钟<br>③ **辅助维度区**（折叠）：Grammar / Vocabulary Receptive / Vocabulary Productive / Sentence Structure —— 明确标注「辅助维度，不产生官方技能等级」<br>④ **证据新鲜度条**：每个技能的最近评估日、reviewDueAt、是否过期 |
| **关键交互** | 任一行 → 抽屉显示原始证据（来源任务、辅助级别、原始作答/产出片段、判定日期、`doNotInfer` 提示）；「加入本周补测」把待确认维度一键塞进候选队列（P0 优先级） |
| **空态** | 某技能无任何证据 → 显示「无基线。系统不会假定你是 0 分，先安排一次基线诊断」，并可一键排入 |
| **错误态** | 证据读取部分失败 → 分区显示「本区数据读取失败」，其余区照常；不得用 0 填充缺失 |

### 4.3 Task Candidate Queue（`/planner/candidates`）

| 项 | 内容 |
|---|---|
| **页面目的** | 展示「所有可做的事」以及「系统怎么排序的」，是解释力最强的页面 |
| **信息架构** | ① **筛选条**：来源类型（复习/复测/核心训练/材料/弱项/拓展/补测）、目标技能、优先级 P0–P3、预计分钟<br>② **候选表**（可排序）：任务名 / 目标技能（+辅助维度）/ 优先级 / 分数（可展开分项）/ 预计分钟 / 最小分钟 / 前置条件 / 证据来源 / 是否 `AI 建议` / 状态（已排入·未排入·因预算未排入）<br>③ **右侧「今日未排入原因」面板**：按原因分组（预算不足 / P0 超额 / 最小粒度不足转周轮换 / 前置未满足），每条给一句话<br>④ **AI 建议区（独立分区，默认折叠）**：AI 提议的候选，每条显示「是否通过调度校验」及未通过原因（如「超出今日预算 20 分钟，已拒绝」） |
| **关键交互** | 展开任一任务的「决策轨迹」→ 显示 7 个分项得分与权重、以及最终 P 级判定；「手动提升优先级」→ 记 `byUser` 并立即影响下次生成（不直接改已确认计划）；AI 建议被拒的条目可「查看原始建议」 |
| **空态** | 候选池为空 → 「当前没有可执行任务。可能原因：题库未导入 / 材料未解析 / 诊断未完成」，给三条具体修复入口 |
| **错误态** | 权重配置非法（和为 0、含负值）→ 页面顶部红条并阻止生成，显示哪个权重越界；不得静默回落默认值（会掩盖配置错误） |

### 4.4 Weekly / 30-Day / 90-Day Plan Builder（`/planner/build`）

| 项 | 内容 |
|---|---|
| **页面目的** | 三层计划的唯一生成入口，且必须让用户感到「我在决定，不是系统在通知」 |
| **信息架构** | ① **层级切换器**：`7 天启动` / `30 天阶段` / `90 天周期`，每层显示当前状态（未生成 / 草稿 / 已确认 / 已过期）与「上次生成时间 + 依据的快照版本」<br>② **7 天**：7 个日期列，每列显示当日预算、已排分钟、任务卡片（含优先级徽章）；顶部显示「首周保守策略：任务量 ≤ 预算 85%」<br>③ **30 天**：周里程碑矩阵（4 行 × N 列：里程碑、技能配比、周测试、材料建议、验收指标、调整条件）；技能配比以「目标 vs 建议」双条对比<br>④ **90 天**：三阶段时间轴（Calibration → Build → Apply & Transfer，标注天数区间）+ 主突破主题 1 个 + 次要主题 ≤2 个 + 复测节点 + 中途校准入口 + 固定免责文案<br>⑤ 底部 **「生成预览 →」**（不直接保存）+ 「保存为草稿」 |
| **关键交互** | 任何编辑先落草稿；「生成预览」产出计划对象并跳 Plan Explanation；上层（90）主题变更时，已确认的下层（30/7）标 `stale` 徽章并给「重新生成」按钮，**不自动改写**；「中途校准」只允许改主题与配比，不改已发生的历史 |
| **空态** | 未确认诊断 → 30/90 层禁用，7 天层可生成但提示「无诊断依据，本计划仅按时间与偏好排程」 |
| **错误态** | 目标冲突（如 IELTS 目标日期 < 30 天但要求 90 天周期）→ 明确提示冲突 + 两个可选处理（缩短周期 / 调整目标日期），不静默取一个 |

### 4.5 Plan Explanation & Trade-offs（`/planner/explain/[versionId]`）

| 项 | 内容 |
|---|---|
| **页面目的** | **本版本最重要的页面**：把「计划为什么长这样」讲清楚，并暴露取舍 |
| **信息架构** | ① **头部**：本次生成的时间、依据快照（版本 + 生成时刻 + 缺失输入清单）、规则版本号、AI 模型/prompt 版本（若有参与）<br>② **逐任务解释卡**（按日期分组，可折叠）：<br>　- 推荐原因（一句话，来自决策轨迹）<br>　- 对应目标（轨道 + 目标等级/分数，若有）<br>　- 对应缺口/待确认维度 → **可点击跳证据**<br>　- 预计分钟 / 最小分钟 / 优先级<br>　- 前置条件（未满足时高亮）<br>　- 预计产出（可判定的产出描述）<br>　- 若不做的影响（可判断时给，不可判断时明确写「无法判断」，**不编造**）<br>　- 来源徽章：`规则` / `AI 建议` / `用户编辑`<br>③ **取舍区（Trade-offs，独立区块）**：<br>　- 「因预算被挤出的任务」列表 + 每条原因<br>　- 「P0 占用 vs 核心训练保障」比例条（如「今日 P0 复习 40% / 核心 40% / 拓展 20%」）<br>　- 「低置信度维度本次被安排为补测，未作为弱项强化」说明<br>　- 「本次未安排的四技能」及原因（如「写作今日无候选任务」）<br>④ **AI 建议处置区**：被采纳 / 被拒绝的建议清单及原因（超预算、前置未满足、与证据冲突） |
| **关键交互** | 点证据链接 → 侧滑证据抽屉（不跳页，保留上下文）；每个任务卡可「我不认同这条理由 → 反馈」（进 P1-02 反馈池）；「返回修改」回 Builder 保留草稿 |
| **空态** | 无 AI 参与时，AI 处置区显示「本次由规则生成，AI 未参与（或不可用）」，而不是隐藏——**隐藏会让用户误以为全是 AI 或全不是 AI** |
| **错误态** | 解释数据缺失（快照被清理）→ 明确显示「本版本的历史解释数据已按保留策略清理，无法追溯」，并禁用「为什么不这样排」的追问入口 |

### 4.6 Daily Budget / Weekly Budget（`/planner/budget`）

| 项 | 内容 |
|---|---|
| **页面目的** | 让用户设定「我到底有多少时间」，并看清这个设定如何影响计划 |
| **信息架构** | ① **周视图**：7 列，每列显示 tierCode、分钟、是否休息日、来源（`USER` / 周模板 / 默认建议）、是否超用<br>② **周总量**：WeeklyTarget（目标分钟）+ 已分配之和 + 差额提示（分配 ≠ 目标时给出「按周内每日分配生效」的说明，避免双口径）<br>③ **档位选择器**：15（应急维护）/ 30 / 45 / 60 / 90 / 120 / 180 / 240 / 自定义，每档附一句「这一档能做什么」的说明<br>④ **休息日管理**：可标休息日；休息日不产生 MISSED、不计完成率分母<br>⑤ **影响预览**：改预算后立刻显示「本周受影响的天数 / 预计被移出的任务数」，并有「查看重排预览 →」 |
| **关键交互** | 改任意一天 → 只影响该天及之后（不改历史已发生天数）；「套用到工作日」批量；任何修改都提示「不会自动重排，需前往重排预览确认」 |
| **空态** | 首次安装：默认 60 分钟并**明确标注「这是建议值，不是你真实可用时间」**（沿用 `DailyBudget.isInitialSuggestion`） |
| **错误态** | 周总量 < 每日分配之和 → 明确警告并给「按周总量压缩」或「提高周目标」二选一；不接受静默以其中一方为准 |

### 4.7 Replanning Preview（`/planner/replan`）

| 项 | 内容 |
|---|---|
| **页面目的** | 重排是破坏性操作，必须先看后做；这是最容易被做成「悄悄改掉」的地方 |
| **信息架构** | ① **触发原因条**：为什么在重排（预算从 60→20 / 跳过周三 / 手动加任务 / P0 复习涌入 / 阶段切换）<br>② **前后对比（核心）**：三列布局 —— `当前计划` \| `变更` \| `重排后`<br>　- 逐任务行：状态标记 `新增`（绿）/ `移除`（红删除线）/ `移动日期`（琥珀，显示 from→to）/ `分钟变化`（显示 40→20）/ `保持`（灰）<br>　- 每组上方显示合计：今日计划分钟 X→Y、预算 Z、P0 占比、被挤出任务数<br>③ **已完成/进行中保护提示**：明确写「已完成的 N 分钟不会被改写」，并列出受影响但保留的任务<br>④ **必填项**：变更原因（默认给建议文案，用户可改）<br>⑤ **底部**：`确认重排`（主按钮）/ `调整参数再算` / `放弃` |
| **关键交互** | 可对单条变更「保留原样」（锁定该任务不参与重排）；对比视图支持只看「有变化的行」；确认后立刻生成新 `PlanVersion` 并展示「已保存为第 N 版」回执 |
| **空态** | 无差异 → 明确显示「本次重排不会改变任何任务」，并禁用主按钮（避免产生无数空版本） |
| **错误态** | 重排后超出预算（不应发生，属防御分支）→ 阻止确认并提示内部错误码；已完成任务被误纳入重排 → 阻止并列出具体任务 |

### 4.8 Weekly Review（`/weekly`，**升级现有页面**）

| 项 | 内容 |
|---|---|
| **页面目的** | 每周一次的结构化复盘 + 「下周只改一件事」 |
| **信息架构** | 保留现有录入（输入/输出/反馈/下周决定）与指标，**新增 5 个区块**：<br>① **本周真正改善的**：对比上周同维度指标（证据数、错误率、延迟复测保持率），标「有证据支持」或「样本不足，暂不下结论」<br>② **仍未解决的**：连续 3 周未改善的维度（标「建议换干预方式」）<br>③ **需要进一步诊断的**：置信度未提升或新出现的 Uncertainty<br>④ **下周 1 个主要突破目标**（单选，AI 可建议 3 选 1，用户选定）<br>⑤ **建议预算与技能配比** + 每条调整的**变更原因** + 「接受 / 部分接受 / 拒绝」<br>⑥ **计划变更阈值说明**：明确展示「本周正确率波动 X%，未达改计划阈值（需连续 2 周 ≥15% 或样本 ≥N），故计划不变更」 |
| **关键交互** | 建议项可逐条接受；接受后才写入下一周 `WeeklyTarget`（`source=SUGGESTION_ACCEPTED`）；拒绝需选原因（太忙/不认同/更想做别的） |
| **空态** | 本周有效学习 < 2 天 → 显示「样本不足，建议仅记录，不调整计划」，且不生成建议（避免基于噪声改计划） |
| **错误态** | 上周计划不存在 → 复盘可做，但配比建议区显示「无上周期基线，仅给参考」 |

### 4.9 Stage Readiness Review（`/planner/readiness`）

| 项 | 内容 |
|---|---|
| **页面目的** | 用证据回答「我能不能宣布这个阶段结束」，并把决定权交回用户 |
| **信息架构** | ① **结论卡**：五种结论之一（Ready for review / Continue current stage / Need targeted practice / Need more evidence / User-approved transition）+ 一句人话解释<br>② **五维证据矩阵**（表格，每维一行）：<br>　- 关键描述能力是否有证据（列出覆盖的子维度）<br>　- 多任务多材料是否表现一致（列出材料数与一致性判断）<br>　- 是否无辅助完成（Baseline 证据条数）<br>　- 延迟复测是否保持<br>　- 新情境迁移证据<br>　每行给 ✓ / ✗ / 数据不足 三态 + 依据链接<br>③ **明确排除项**（反例展示）：列出「**不参与判定**的指标」——学习天数、教材完成率、单次 AI 分数，并显示它们当前的值（让用户看到"它们有多好看但不作数"）<br>④ **切换动作**：`确认进入下一阶段`（需填写确认人=本人 + 备注）/ `继续保持当前阶段` / `安排针对性补练` / `先补证据` |
| **关键交互** | 点任一证据行进抽屉；「先补证据」自动把缺口项排入候选队列；确认切换写 `StageTransitionLog`（append-only）并提示「将影响后续计划生成」 |
| **空态** | 阶段刚开始（< 7 天）→ 「阶段早期，readiness 判定无意义」，只显示已收集证据计数 |
| **错误态** | 五维中任一维度读取失败 → 该行显示「数据读取失败」，且**整体结论必须是 Need more evidence**（不允许在缺数据时给 Ready） |

| 项 | 内容 |
|---|---|
| **页面目的** | 审计与回滚。回答「我的计划被改过几次、每次为什么、第 3 版和第 7 版差在哪」 |
| **信息架构** | ① **版本时间线**（左列）：每个版本一行 —— 版本号、日期范围（日计划=单日，周/30/90=区间）、变更来源（生成/重排/手动调整/回滚）、变更原因、预算、操作者（本人/系统）、生成耗时与 AI 参与情况<br>② **对比选择器**：任选两个版本 → 差异视图<br>③ **差异视图（核心）**：分三栏 `仅旧版有` \| `变更` \| `仅新版有`，逐任务列出模块/技能/分钟/优先级/日期变化；顶部汇总「总分钟 320→280」「P0 任务 3→5」「四技能配比 30/30/25/15 → 25/30/25/20」<br>④ **快照可追溯性**：每个版本显示「依据快照 #N，生成于 T，规则版本 R，AI 版本 M」；快照已被清理时明确标注<br>⑤ **恢复动作**：`恢复此版本`（生成新版本，备注「恢复到第 N 版」）、`导出该版本说明`、`与此版本对比当前` |

| **错误态** | 版本快照损坏/缺失 → 仍可看元数据，差异视图显示「快照缺失，无法逐条对比」，禁用恢复 |

## 7. 待确认问题（需主理人拍板）

> 每项给 2 个选项 + 推荐 + 影响面。

### Q1 三层计划（7/30/90）的激活关系与切换语义

| | 选项 A（推荐）**嵌套 + 单向下依赖** | 选项 B 三层独立平级 |
|---|---|---|
| 关系 | 90 天是容器 → 30 天是其中阶段 → 7 天是 30 天的第一周细化。上层变更使下层标 `stale` 并给「重新生成」入口，**不自动改写** | 三层各自独立生成，互不约束 |
| 优点 | 用户心智一致（"我在第 2 个 30 天"）；证据/主题能贯穿；符合需求 §6 的「启动/阶段/周期」递进语义 | 实现简单，互不阻塞 |
| 缺点 | 需处理 stale 传播与重生成提示 | 三层目标可能互相矛盾（30 天说要攻写作，7 天排满听力），用户无法判断哪个算数 |
| **推荐理由** | 违反一致性的计划等于没有计划；且"不自动改写已确认版本"本就是 G3 的要求，恰好可用 stale 标记解决 | — |
| **影响面** | 数据模型（`PlanVersion` 加 `layer` 与 `parentVersionId`）、Builder 交互、Dashboard 待确认区 | 无 |

### Q2 AI 建议超出预算时：拒绝还是裁剪

| | 选项 A（推荐）**拒绝 + 确定性补位 + 记录原因** | 选项 B 自动裁剪到预算内 |
|---|---|---|
| 行为 | scheduler 校验 AI 提议的分钟数，超预算 → 整条拒绝，落 `RejectedAiSuggestion(reason='OVER_BUDGET')`，再由确定性规则补位 | 按比例削减 AI 建议分钟数使其适配预算 |
| 优点 | 归因清晰（"AI 建议了 60 分钟，预算 20，已拒绝"）；不会造出 AI 没提议过的任务 | 预算利用率更高 |
| 缺点 | 预算紧张时 AI 建议可能几乎全被拒 | 裁剪后的任务既不是 AI 原意也不是规则结果，**责任归属不清**；用户看到"AI 建议"徽章但内容是裁剪产物=误导 |
| **推荐理由** | 需求 §7「scheduler 必须拒绝或调整」二选一，选拒绝。裁剪会污染 `byAi` 标记的可信度，而可信度是本版本的核心资产 | — |
| **影响面** | AI prompt 设计（需明确告知预算上限）、Plan Explanation 的 AI 处置区、Candidate Queue 的 AI 分区 | — |

### Q3 每周技能权重：自动微调还是仅建议

| | 选项 A（推荐）**仅建议，用户确认后生效** | 选项 B 自动微调（事后通知） |
|---|---|---|
| 优点 | 符合 G3「确认权」；用户知道自己为什么被改了配比；避免振荡 | 减少操作摩擦 |
| 缺点 | 每周多一次确认动作 | 违反「AI 不得无提示改写已确认计划」；且配比是周维度的强意图，自动改易引发困惑 |
| **推荐理由** | 现有 `WeeklyTarget.source` 已有 `USER` / `SUGGESTION_ACCEPTED` 两态，说明系统设计上本就要求确认；A 零新增结构 | — |
| **影响面** | Weekly Review 交互、`WeeklyTargetSuggestion` 是否必需（B 则不需要） | — |

### Q4 版本历史保留粒度：每次生成 vs 每次确认

| | 选项 A（推荐）**确认点才生成 `PlanVersion`；预览/放弃只记轻量 `ReplanningEvent`** | 选项 B 每次生成都生成版本 |
|---|---|---|
| 优点 | 历史干净（每条都是真实生效过的计划）；对比有意义；存储可控 | 完整留痕，可审计"被放弃的方案" |

| **推荐理由** | 需求 §12 的「可审计」指**生效决策**可审计，不是操作日志全量；且 `PlanVersion` 已有 `idempotencyKey`，说明它面向"一次生效" | — |
| **影响面** | `PlanVersion` 的使用语义、`ReplanningEvent` 的必要性、History 页文案 | — |
| **附带问题** | `PlanningSnapshot` 保留多少份？（建议：最近 20 份 + 已被版本引用的永久保留；超出按 FIFO 清理，清理后 History 明确标注「快照已清理」） | — |

### Q5 【冲突项，必须拍板】`stageGate.ts` 的 H4（近 30 天净时长 ≥240 分钟占比 ≥80%）

| | 选项 A（推荐）**降级为参考指标 + 改为相对预算** | 选项 B 保留原样作为晋级门槛 |
|---|---|---|
| 行为 | H4 不进 readiness 结论，只在 Readiness 页作为「投入稳定性」参考；阈值改为「净时长 ≥ 当日预算 × 60% 的日期占比」 | 维持 240 分钟绝对门槛 |

| **影响面** | `stageGate.ts`、`constants.ts:GATE_H4_MIN_MINUTES`、`stageGate.test.ts` 回归；`/stages` 页面文案 | — |

### Q6 候选池与 v2.6 `TaskProposal` 的确认路径归属

| | 选项 A（推荐）**单一确认入口**：材料任务在 v2.7 候选池中确认后写 `PlanTask`，材料页的「确认草案」改为跳转到候选池 | 选项 B 两条路径都可确认（材料页 + 候选池） |

### Q7 `Uncertainty` 的判定阈值来源

| | 选项 A（推荐）**沿用 `WEAKNESS_MIN_QUESTIONS` + 叠加 `SkillProfile.confidence`** | 选项 B 为 v2.7 另设新阈值 |
|---|---|---|
| 优点 | 与现有弱项判定口径一致，用户不会看到两套"证据够不够"的标准；零新增常量 | 可针对规划场景调优 |

## 9. 最大风险（供主理人决策参考）

**最大风险：可解释性变成"第二套真相"。**

如果 `explanation`（推荐原因、证据引用、分项得分）与 `generateAdaptivePlan` / `prioritizeCandidates` 的实际计算是**两次独立计算**，那么 UI 展示的理由会与真实排程原因不一致——而它看起来"有据可查"，因此比 AI 幻觉更难被发现，也更伤信任。这是本版本特有的风险：v2.6 的幻觉风险有 `SourceVerifier` 兜底（引文必须命中原文），而计划解释**没有原文可对**。

**缓解措施（已写入 P0-09 为硬要求）**：
1. 解释必须由排序函数的**同一次调用**返回的 decision trace 直接落库，禁止任何形式的二次计算或事后推断；
2. `explanation.evidenceRefs` 必须是可解析的真实 ID（AC-8 的测试强制）；
3. 「若不做的影响」不可判断时**必须**输出「无法判断」，不允许生成看似合理的推测；
4. 解释文案可由 AI 润色，但 AI **只能改措辞，不能增删理由成分**——润色前后的 structured 字段必须 diff 相等（可作为一条测试断言）。

**次要风险：AI 从"建议"悄悄变成"决定"**。若确定性候选池供给不足，工程上最容易的补法就是"让 AI 多生成一些候选"，久而久之 AI 决定了计划的实际内容。缓解：AI 只能从既有候选池中挑选与排序解释，**不能新增池外任务类型**（已写入 §5.3 与 Q2）。
