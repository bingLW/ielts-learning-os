# v2.7 调度算法说明（Scheduler Spec）

> **这份文档是写给使用者看的**：你需要知道「系统为什么这样排」，以及「哪些现象不是 bug」。
> 架构与实现细节在 `41-v2.7-architecture.md` §2.4；两者不一致时以 `41` 为准，并请把这份也改过来。
>
> 适用范围：v2.7 的**候选评分与优先级**（哪个任务先做）。
> 不适用范围：预算怎么算（见 `/planner/budget` 页与 `getEffectiveBudget()`）、阶段怎么晋级（见 `/planner/readiness`）。

---

## 1. 一句话概括

系统把当天所有「可做的事」收集成一个**候选池**，给每条候选打一个 0–1 的分，再按分会成 P1/P2/P3 三层；
但**到期复习与到期复测不受分数管，一律 P0**。分数只回答一个问题：**在都不是「今天非做不可」的事情里，先做哪一件。**

---

## 2. 七个因子

每个因子输出一个 0–1 的数，**越大越该排前面**。加权求和得到总分。

| # | 因子 | 含义（人话） | 默认权重 |
|---|---|---|---|
| 1 | **urgency** | 离到期还有多久 / 逾期几天 | **0.22** |
| 2 | **goalRelevance** | 这件事离你的目标还有几步（用 90 天周期折算） | **0.18** |
| 3 | **evidenceStrength** | 这件事对应的缺口有多严重、证据有多硬 | **0.20** |
| 4 | **errorRecurrence** | 近 28 天同类错误出现过几次 | **0.12** |
| 5 | **prerequisiteReady** | 前置条件是否满足（二值：满足 1 分，不满足 0 分并被标为「被阻塞」） | **0.10** |
| 6 | **timeCost** | 这件事有多短（越短越高，同等条件下先做短的） | **0.10** |
| 7 | **preferenceFit** | 你是否曾把这类模块标为「合适」 | **0.08** |

> 权重合计 **1.000**。设计意图：`urgency + evidenceStrength = 0.42`，让「到期」和「真有证据的缺口」主导；
> `timeCost` 只有 `0.10`，避免整个计划退化成「只做 5 分钟小任务」；`preferenceFit` 最低，防止个人偏好压过证据。

### 2.1 某个因子没有数据时怎么办 —— **判据只有一句**

> **这个「缺失」是「确认为无」，还是「不知道」？**

| 缺失的性质 | 语义 | 回落值 |
|---|---|---|
| **确认为无** | 查过了，确实没有 | **`0.00`** |
| **不知道** | 没测过 / 没关联过 / 没表达过 | **中性值**（`0.30`~`0.50`），绝不是 `0` |

把「不知道」写成 `0` 的后果不是「保守」，而是**把缺失当成负面证据**：一个从没测过的维度会被系统性压低，永远排不上。

逐个因子的具体数值与理由：

| 因子 | 缺失情形 | 性质 | 回落值 | 理由 |
|---|---|---|---|---|
| `urgency` | 没有到期日 | 确认为无紧迫性 | **`0.00`** | 不是复习/复测任务就没有到期压力。若给中性值，普通核心任务会被无端抬到 P1 |
| `errorRecurrence` | 近 28 天没有同类错误（且该维度**确实练过**） | 确认为无重复错误 | **`0.00`** | 没见过重复错误，就不该被「错误顽固度」加成 |
| `evidenceStrength` | 任务未关联任何已证实缺口 | **不知道这任务价值几何** | **`0.30`** | 「无缺口关联 ≠ 无价值」：阶段核心训练本来就可能不对应任何缺口。加权贡献 `0.20×0.30=0.06` 而非 `0`，这 0.06 足以让同一候选从 P2 掉到 P3（这正是我们希望的可观察差异） |
| `goalRelevance` | 没有学习周期 / 没有目标日期 | **不知道与目标的关系** | **`0.50`** | 公式假设「有一个 90 天周期在跑」。没有周期时给 `1.0` 会让所有候选满分、该因子失效；给 `0` 会让所有候选被同等打压 |
| `preferenceFit` | 你从未表达过偏好 | **不知道偏好** | **`0.50`** | 无偏好 ≠ 不喜欢。给 `0` 等于把所有没评价过的模块系统性排到后面 |
| `prerequisiteReady` | —— | 二值 | 不适用 | 前置满足与否是确定事实，不存在「不知道」这一档 |

### 2.2 一个已知的口径局限（`errorRecurrence`）

`errorRecurrence = 0.00` 只在「该维度**确实练过**」时才等价于「无重复错误」。若 28 天内该维度**一次都没练**，那是「没有观察」而不是「没有错误」。

当前口径**仍然返回 `0.00`**，理由：错误重复度是**加重因子**而不是**发现因子** —— 未观察的维度应该由「补测（PROBE）」路径接手，而不是靠这个因子被抬升。

但系统会**区别显示**这两种情况：
- 决策轨迹里会标「近 28 天无记录（**未观察**）」，而不是「0 次错误」；
- 你可以在 `/planner/candidates` 的决策轨迹里看到这个标注。

（若后续能稳定拿到「该维度是否练过」的信号，可升级为「未观察 → 中性 `0.30`」。那属于口径变更，会递增 `weightsVersion`。）

## 3. P0–P3 是怎么定的 —— **P0 不由分数决定**

```
到期复习 / 到期复测（sourceKind ∈ {REVIEW, RETEST} 且到期）  → P0   ← 约定，不看分数
否则 score ≥ 0.60                                          → P1
否则 score ≥ 0.42                                          → P2
否则                                                        → P3
```

### 3.1 为什么 P0 不看分数

**P0 是约定，不是排名。** 到期没做的复习会按间隔曲线衰减 —— 今天不做，明天做同一件事的收益更低。所以它是「今天非做不可」而不是「今天最值得做」。

如果让 P0 由分数决定，一次「与目标高度相关」的拓展任务（比如 `goalRelevance` 拉满、总分 0.95）就可能把到期复习挤到 P1 —— 而这种挤占**在页面上完全看不出问题**：两条都在今天的列表里，只是顺序不同。等到复习曲线断了，原因已经查不到了。

所以：**分数只决定 P1–P3 的分层与同层顺序，以及 P0 内部谁先谁后。** 你看到「一个拓展任务分数更高却排在到期复习后面」，那不是 bug，是设计。

排序的确切顺序是三层，逐层决胜：

```
先按优先级：P0 → P1 → P2 → P3        ← 所以 P0 恒在最前，不看分数
再按分数：由高到低                     ← 只在同一优先级内部比
最后按稳定标识：升序                    ← 保证同分也有确定顺序
```

最后那一层看起来无关紧要，但它保证「同样的输入得到同样的排列」—— 没有它，两条同分任务的先后就由数据库的返回顺序决定，而那个顺序会随时间变化。

### 3.2 三个阈值

| 阈值 | 值 | 作用 |
|---|---|---|
| `p1` | **0.60** | `score ≥ 0.60` → P1 |
| `p2` | **0.42** | `0.42 ≤ score < 0.60` → P2；`score < 0.42` → P3 |

阈值边界是**闭区间**（`= 0.60` 归 P1）。任何对阈值的修改都必须同时递增 `weightsVersion` 并重算历史 —— 否则同一个分数在两张页面上会显示两个优先级。

### 3.3 三个比例（作用在「装箱」阶段，不在评分阶段）

评分只给出「谁更重要」，**实际排进一天里还要过装箱**。这三项决定装箱时的约束：

| 参数 | 默认 | 作用 |
|---|---|---|
| `p0CapRatio` | **0.6** | P0 最多占当日预算的 60%。剩下的留给核心训练与拓展 —— 否则一个「复习爆掉」的日子会把当天变成纯复习日 |
| `coreMinRatio` | **0.3** | 预算再紧也留 30% 给 P1（当前阶段核心学习）。防止复习与杂项吃掉全部时间，导致阶段推不动 |
| `bufferRatio` | **0**（不启用） | 预留缓冲，扣掉「计划外的必然损耗」。`0` 时与不启用逐字等价 |

> 这三个参数可被 `priorityPolicy`（预算策略）覆盖，但**改它们不会改变候选的分数**，只改变一天里怎么装。所以「改了 `p0CapRatio`，为什么某条任务分数没变」是正常现象。

## 4. `weightsVersion` 是什么，为什么必须递增

系统给每次评分结果记一个 `weightsVersion`（当前 `w1`）。它标记「这批分数是用哪一版权重算出来的」。

**规则：只要改了权重或阈值，就必须递增 `weightsVersion`。** 理由很实际：

- 历史决策（`/planner/history`）里存的是**当时的**分数与优先级。若权重变了而版本号没变，回看历史时无法判断「这条 0.58 是旧权重下的 0.58 还是新权重下的 0.58」；
- 于是「当时为什么这么排」这个问题的答案就永久丢了 —— 而这正是 v2.7 最想保住的东西。

同样的道理：派生分钟表（不同题型的估算时长）、优先级阈值，都进同一次「输入指纹」。所以**改一次默认时长表，也会让计划重新计算** —— 因为候选的分钟数变了，装箱结果就会变。

### 4.1 可复算的依据是什么（`rationale` 不在其中）

`rationale`（推荐理由文案）**不是**复算依据。同一条决策在两次重算中，如果一次开了 AI、一次没开，
`rationale` 会不同（措辞不同、事实相同），但 `factorsJson` / `score` / `priority` / `weightsVersion` 必须逐字一致。

因此「当时为什么这样排」的回答顺序是：**先看 `weightsVersion` + `factorsJson` + `score` + `priority`**，
再看 `rationale` 作为人话解释。AI 只被允许改 `rationale`（`assertReasonOnlyChanged` 逐字段复核），
任何试图改 `priority` / `factors` / `eligibility` 的建议都会被拒为 `REJECTED_AI_MUTATED_DECISION`。

## 5. 开放题（`OPEN_TASK`）的时长覆写

诊断题库里的 `OPEN_TASK` 是**唯一一个「同一种题型、耗时差 2–3 倍」**的题型：它既可能是 40 分钟的大作文，也可能是 3 分钟的口语短答。所以系统按技能覆写它的估算时长：

| 技能 | 估算 | 说明 |
|---|---|---|
| `WRITING` | **20 分钟** | 写作开放题（paragraph / essay 级） |
| `SPEAKING` | **10 分钟** | 口语开放题 |
| 其余（`READING` 等） | **15 分钟** | 基础默认值 |

**为什么只有这一档**：其余题型（`MCQ` / `SHORT_ANSWER` / 材料域五类）的技能差异**不改变量级**，分档只会把一张时长表拆成两张互相打架的表 —— 同一个题型出现两个值，谁生效取决于代码里的判断顺序。

**一个附带的实际收益**：开放题的**最小可执行单元等于估算时长**（不可拆）。覆写之后，一篇写作开放题的最小单元从 15 分钟变成 20 分钟 —— 于是它**不会再被塞进一个 15 分钟的「应急日」**。覆写不只是让估算更准，它让「放不下」在装箱阶段就显现出来。

> 已知局限：20 / 10 仍是**粗估**。一篇真正 40 分钟的大作文仍会被排在很后面。这条记在 `47-v2.7-known-limits.md`。

## 6. 这一节**不承诺**什么

写清楚，以免把系统的输出当成别的东西：

| 不承诺 | 说明 |
|---|---|
| **不预测 IELTS 分数** | 系统排的是「接下来做什么」，不是「你能考几分」。没有任何分数预测模型 |
| **不由完成率推等级** | 完成率只影响「本阶段是否推进」的讨论，**不**反过来推出你处于哪个等级。等级来自证据与测试 |
| **不做「达到 X 分需要多少小时」的预测** | 这类预测在数据量不足时误差极大，且会给出虚假的确定性。系统只按你的实际预算排，不给时间-分数换算 |
| **不保证「排进今天 = 今天做得完」** | 装箱用估算时长，估算偏小就会超时。超时不会自动顺延到明天（需你在重排时确认） |
| **不保证 P1 比 P3 更重要** | P0 之外的分层是「同等条件下的先后」，不是价值判断。P3 的拓展任务对长期有用，只是今天排在后面 |

## 7. 常见「看起来像 bug，其实不是」

| 现象 | 原因 |
|---|---|
| 拓展任务分数很高却排在到期复习后面 | P0 是约定，不看分数（§3.1） |
| 两个任务分数一样，顺序却每天都不同 | **这是缺陷，不是正常现象** —— 如果同一个任务的相对位置每天变，那不是「系统在轮换」，是 bug。排序是确定的：**先按优先级（P0→P3），再按分数从高到低，最后按候选的稳定标识升序**。同样的输入必须得到同样的排列，否则「当时为什么这样排」就无法复算 |
| 改了 `p0CapRatio`，任务分数没变 | 那三个比例作用在装箱，不在评分（§3.3） |
| 某个任务「价值很高」却只得 0.30 的证据分 | 它没有关联任何已证实缺口 —— 这是中性值，不是否定（§2.1） |
| 一个从没练过的维度没有被排上来 | `errorRecurrence` 的回落在「未观察」时仍是 `0.00`（§2.2）。它会由补测路径接手 |
| 改了时长估算表，所有计划的分数都变了 | 分钟数进「输入指纹」，装箱结果随之变化（§4） |
