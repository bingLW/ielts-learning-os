## 3. Known Issues

### 3.1 D1 的修法与 PRD 伪代码原文顺序不一致（文档待同步）

PRD §6.1 伪代码（`docs/01-prd.md:186-189`）写作：

```
if total == 0:            return PENDING
if correct > total:       return error
```

修复后实现把 `correct > total` 提到 `total === 0` **之前**。业务上更安全（拒绝脏数据），且不违反 PRD「边界约定 4」列举的顺序（PENDING → 硬否决 → 正确率档 → 降权档，其中并未列出 `correct>total` 的位置）。
**建议**：请产品同步修订 PRD 伪代码，否则后续任何人「按 PRD 对齐」都可能把它改回去，导致 `color.edge.test.ts` 的 D1 用例重新变红。

### 3.2 D9 的 `CAPACITY_EXCEEDED` 拦截点当前不可达（防御性分支）

`generateDailyPlan` 的容量校验在 `plan.ts:259-265`，但合法入参区间为 240–300，即 `extra ≤ 60`；按 `plan.ts:63-89` 的 `moduleCapacity` 逐项算，三个阶段的**最小**容量总和为：

- 固定项（与阶段无关）：VOCAB 15 + LISTENING 20 + READING 20 + SPEAKING 20 + WRITING 15 + EXTENSIVE 15 = **105**
- **S1 = 105**：`T=240/270` 时 `GRAMMAR 容量 = max(0, min(15, floor(0.2T) − 40 − 15)) = 0`（40 = GRAMMAR 基础值，15 = 基础 SENTENCE）；`T=300` 时为 5 → 合计 **110**
- **S2 / S3 = 125**：105 + 语法 15 + 句子成分 5

> 与早期版本的差异说明：此前记录的「S1 = 120」是错的。差异来自 D4 修复后 `moduleCapacity` 的 GRAMMAR 分支**必须先扣掉基础 SENTENCE 15 分钟**（否则语法一加就会把「语法类合计」顶过 20%），因此合法区间内 S1 的语法容量是 0（T=240/270）或 5（T=300），而不是 15。

`60 < 105`（余量至少 45 分钟），所以通过公开 API **永远触发不到**该分支。已把测试改成断言「合法区间内不得误报 `CAPACITY_EXCEEDED`，且 Σ 仍严格等于 `dailyMinutes`」，把该分支定位为**防御性代码**。
**建议**：保留（防未来放宽上限/新增模块），但在代码注释里标注「当前不可达」，避免被误读为已覆盖路径。

> 附注：`plan.test.ts` 的 D9 压测用例直接调 `allocateExtra(200, 基础版, [], 'S1_A0_A2')`，此时 `totalMinutes = 440`，语法容量恢复为 15、合计 120，故断言 `Σ = 360`。两组数字（105/110 与 120）不矛盾，差别只在 `T`：前者是合法区间（T ≤ 300），后者是压测构造的 T = 440。

### 3.3 D6：补录历史首测时复习点会塌到同一天（未修）

`review.ts:38-41` 的 `dueDateFrom = max(d0 + n, today)` 保证「新点不落过去」，但副作用是：若用户补录一个月前的首测（Q8「补录历史日期」是明确支持的场景），D1/D3/D7 会全部落在 today，三个复习点变成同一天三条，节奏语义丢失。
**现状**：该行为已被 `review.edge.test.ts` 用一条「已确认实现」用例固定（断言 D3/D7 均 clamp 到 today，并注明 D6），因此不是静默行为。
**建议方案**（需产品裁决，二选一）：
1. 保持 clamp，但生成时把已过去档位直接落 `SKIPPED` 并在 UI 提示「D1/D3 已错过，从 D7 开始」；
2. 按自然日保留 `dueDate` 并允许逾期（与「逾期不消失」一致），由复习队列的「逾期」Tab 承接。

### 3.4 D12：日/周时长只能来自 `StudySessionDaySplit`（不变量，已确认无重复 join）

已确认查询层不存在 `StudySession` 的多重 join，**无重复计数**。但该性质依赖一条**必须写进规范的不变量**：

> 日/周/阶段口径的「净时长」只能对 `StudySessionDaySplit.minutes` 求和；**不得**与 `StudySession.activeMinutes` 混算，也不得用 `endedAt - startedAt` 现算。跨零点拆分只在 `StudySessionDaySplit` 层发生（PRD §7 全局约束「所有 `*_date` 禁止存时刻；跨日拆分仅在 session 层处理」）。

### 3.7 D14（打分侧）+ D15（展示侧）：`rankWeaknesses` 同 key 合并的两个独立错误（**均已修复**）

**共同背景**：同一 key 多来源合并时，有三个地方需要**三种不同**的合并口径，混用任意两处都会产出用户可见的错误。这也是为什么必须拆成两个缺陷号记账：

| 用途 | 正确口径 | 混用后的后果 |
|---|---|---|
| `minQuestions` 阈值 | 题量**累加**（它衡量「证据有多少」；裁决 B，见 §3.8） | 用 max 会让本该合格的样本被判「数据不足」 |
| 打分 | 各分项 **max**（PRD §6.5：不累加，避免同一维度被多来源放大） | 用「分子 max + 分母累加」重算 → **D14** |
| 依据文案 | 取**同一样本**的原始分子分母（最差来源） | 用 candidate 上的混合值 → **D15** |

#### D14（打分侧）：错题率被稀释

```
两个来源都是「错 5 / 10」
  totalQuestions = 10 + 10 = 20    （+= 相加）
  wrongQuestions = max(5, 5) = 5   （max）
  → errRate = 5 / 20 = 0.25        （按 PRD「各分项取 max」应为 0.5）
  → score   = 0.35 × 0.25 = 0.0875 （应为 0.35 × 0.5 = 0.175，被稀释一半）
```

**为什么隐蔽**：合并后样本量（20）仍然过阈值，门槛不报错；分数只是「偏低一点点」，排序错位既不抛异常也不崩。副作用是：同一知识点在多个来源（科目级 + 知识点级 / 错题 + EGIU 单元）重复出现时，**错得越集中反而被稀释得越厉害**，真正的重灾区被往后压。

#### D15（展示侧）：依据与结论自相矛盾

即使 D14 修好（打分用 0.5），只要 `buildEvidence` 还读 candidate 上的混合值，卡片就会写「错 5/20 题」——一张读作 25% 的卡片被排到第一名。两种退化都必须挡住：

```
反例 A（分子 max + 分母累加）：9/10 + 0/10 → 「错 9/20 题」，读作 45%，而打分是 90%
反例 B（取错来源）           ：9/10 + 0/10 → 「错 0/10 题」，读作 0%，却排在第一名
正解                         ：9/10 + 0/10 → 「错 9/10 题（最差来源）」
```

> **为什么原来的用例挡不住**：D14 那条用的是「5/10 + 5/10」——它只能挡住「分子 max + 分母累加」（得 5/20 = 0.25）；但**如果连分子也累加**，10/20 = 0.5 与正解 max(0.5, 0.5) = 0.5 **完全相同**，用例照样绿。也就是说「按比例相同」的输入无法区分「取各来源比率的 max」与「把两来源整体累加」，而后者在同一维度被多来源重复统计时会放大权重（正是 PRD §6.5 要禁止的）。展示侧同理：「错 5/20」与「错 10/20」都不等于「错 5/10」。所以 D15 必须用 **9/10 + 0/10** 这种**不对称**输入——两种退化都落到 9/20 = 0.45，与正解 0.9 明确分离。

#### 修法（两步，均已静态复核）

1. **D14**：`mergeCandidates` 返回 `MergedEntry { candidate, parts, bestErr, bestReview, bestUnit, evidenceQuestions, sourceCount }`；`parts` 逐项 `Math.max` 后**一路带到打分**，`rankWeaknesses` 直接 `scoreOf(parts)`，不再对合并后的 candidate 重新 `partsOf`。
2. **D15**：三对计数各配一个 `SamplePair`（`bestErr` / `bestReview` / `bestUnit`），每对**整对**被新来源接管、绝不跨来源拼装；合并结束后由 `applyPairs` 统一回写 `candidate`；`sourceCount` 记录来源个数，`buildEvidence` 在 `sourceCount > 1` 时给比率段追加「（最差来源）」，避免被读成该维度全量统计。

**静态复核（`weakness.ts:100-135` / `165-193` / `202-273` / `283-287` / `326-362`）**：

- `MergedEntry` 的字段注释把「阈值用 `evidenceQuestions` 累加、打分用 `parts` max、展示用三对 `SamplePair`」的口径写死在类型上，并显式警告「拿 `candidate.totalQuestions` 判阈值会埋掉分散来源，拿 `evidenceQuestions` 做展示就是 D15」（`100-121`）；

#### 顺带的两处口径调整（一处不改输出，一处**改**输出）

**(1) 不再「保留首个来源」**：`reviewTotal` / `unitTotal` 原先是首个来源的快照，与 `reviewOverdue` / `unitRed`（取 max）天然不同源，属同一类跨来源拼装隐患。现已改为**整对取自同一条来源**（`147-154` 的 `applyPairs` 统一回写），一对内部不可能再出现「分子来自 A、分母来自 B」。

**(2) 逾期 / 红灯改按「分子」挑来源（会改变用户可见文案，已登记）**：`bestReview` / `bestUnit` 不看比率，改看分子（逾期条数 / 红灯单元数），分子相同再比比率（`shouldReplaceCount`，`185-193`）。原因：这两项是**待办量**，用户读到「逾期 3 条」的意思是「我今天要清 3 条」。

```
同 key 两来源：A = 逾期 3/4（0.75）   B = 逾期 5/10（0.5）
按比率挑（旧）→ 选 A → 卡片「逾期复习 3 条」，而实际有 5 条待清
                用户清完 3 条后卡片不再提示，还剩 2 条悬着
按分子挑（现）→ 选 B → 卡片「逾期复习 5 条」✅（少报待办比「分母不同源」更糟）
```

因此本轮三处挑法是**故意不同**、不是疏漏：`errRate` 按**比率**（排序依据）、逾期/红灯按**分子**（待办量），统一铁律只有一条——**每一对分子分母必须来自同一个来源**。

> **覆盖状态：已补齐（口径 C 用例）**。新增前，24 条 `weakness` 用例中没有任何一条覆盖多来源的逾期/红灯合并（其余用例的 `reviewTotal` / `unitTotal` 都是 0 或单来源），是「改坏不会红」的洞。现由 `weakness.test.ts:394`「逾期按分子挑：3/4 的 0.75 不得盖掉 5/10 的 5 条」单独守住（独立 describe）。

**口径 C 的判别性样本与它锁住的两件事**：同 key 两源、错题数完全相同（各 `错 4/20`），只有逾期不同——A `3/4`、B `5/10`。

```
evidenceQuestions = 20 + 20 = 40 ≥ 10 → 进 Top3
parts.reviewDebt = max(0.75, 0.50) = 0.75（打分侧取 max，与「挑哪条来源展示」无关）
bestReview 按分子选中 {5, 10}（shouldReplaceCount(5,10,3,4) = 5 > 3 → true）
evidence  = 「错 4/20 题（最差来源） · 逾期复习 5 条」
actionHint = 「先清 5 条逾期复习，再追加 15 分钟专项练习」
倒序传入：shouldReplaceCount(3,4,5,10) → 3 < 5 → false → bestReview 保持 {5,10}，两次结果逐字段相同
```

它锁两件事，缺一不可：
1. **`evidence` 说 5 条、不说 3 条** —— 挡住「按 rate 挑」的退化（0.75 会赢过 0.50，少报 2 条待办）；
2. **`actionHint` 也是 5 条** —— `buildActionHint`（`:309-317`）读的是同一对字段；只断 `evidence` 的话，「改 `evidence` 不改 `actionHint`」的实现照样绿，而那仍是用户可见的自相矛盾（卡片说逾期 5 条、建议清 3 条）。

> **它是 `shouldReplaceCount` 的唯一防线**：三条 D15 用例都只覆盖错题率（rate 口径），把这个函数换回 `shouldReplaceSample` 它们会全绿，而界面上的待办数会静默少报。

#### 平局规则（D15 衍生）：errRate 相同取样本量更大的来源

「最差来源」的判定不能只看比率，还要看证据厚度：`错 1/2`（50%）与 `错 5/10`（50%）比率相同，若按「保留先出现的」处理，查询层一条 `ORDER BY` 就能把「错 1/2 题」这种极薄样本摆上 Top3 卡片。现实现为：

```
【错题率（shouldReplaceSample，165-173）】
比率更高者胜
比率相同 → 取「原始题量更大」的那个来源
          比较基准必须是当前最差来源的 bestErr.denominator，不能用 candidate.totalQuestions
          （后者是首个来源留下的值，与 bestErr 不同源）

【逾期 / 红灯（shouldReplaceCount，185-193）】
分子更大者胜（待办量）
分子相同 → 比率更高者胜（同一对里分子相同 ⇒ 分母更小者胜，必分胜负）
```

两条规则都让取值**与来源顺序无关**，同一知识点无论查询层先返回哪条来源，卡片依据都一致（比「幂等」更强的性质）。错题率那条已用「正序 / 倒序 `toEqual`」钉死（`weakness.test.ts:366`）。

> **两种平局判据在 ≥3 个同率来源时才会分叉**（两来源场景同解，所以现有用例测不出差异）：来源依次为 `1/2 → 5/10 → 3/6`，三者都是 50%——按「比当前最差样本」得 `错 5/10`，按「比首个来源」得 `错 3/6`。**这是用户可见差异**（卡片上写的就是不同的两个分数），不是纯实现细节。
> 本轮团队裁决**不加**这条断言（理由：三种挑法在同率时的差异不影响「该不该补」的排序结论，且换实现时容易误报）；我按要求未加，登记在此作为**已知覆盖缺口**——若将来有人把比较基准从 `bestErr.denominator` 改成 `candidate.totalQuestions`，现有用例不会红。

> 剩余的顺序依赖（文档已声明，不视为缺陷）：`name` / `mainErrorCategory` / `trendDelta` 仍取**首个**出现的来源（名字是用户可读标识，不该被另一条来源改写），因此 DTO 整体只是**部分**与顺序无关——**断言不要按「完全顺序无关」写**。
>
> 注意 `weakness.test.ts:366` 那条倒序 `toEqual` 之所以成立，前提是该用例两条来源的 `name` 都是 `听力`、`mainErrorCategory` / `trendDelta` 都是 `undefined`：唯一可能随顺序变化的量就是三对计数，而它们已被证明与顺序无关。换一组 `name` 不同的输入去倒序 `toEqual`，**必然红**——那是设计使然，不是缺陷，照抄这个模式去测 `name` 会误报。

#### 措辞边界（说明，不加断言）

「（最差来源）」后缀的触发条件是 `sourceCount > 1`，**不是**「这三个数是否真的来自不同来源」（`weakness.ts:286`）。极端情况：两条来源只有逾期数不同、错题率完全相同且分母也相同 → 仍会打后缀，尽管那个分数恰好等于两条来源的值。这是**有意的保守措辞**（宁可多标一次，也不让人把单来源数字误读成该维度全量统计）。

测试只锁「多来源必须带后缀」（`:336`）与「单来源必须没有后缀」（`:157` 整串精确比对），**不锁**上述边界的具体措辞——锁死措辞会让一次纯文案优化变成红测试。

| `:350-354` | `eligible` 与 `insufficient` **两个** filter 都读它 |

**裁决理由（与我的 QA 意见一致）**：PRD §6.5 原文是「该维度**总题数** < 10」——「该维度」是**维度级**，不是单条来源级。两源各 6 题合计 12 道题的证据，判「数据不足」会系统性埋掉「知识点分散在多来源」的维度，而那正是最该被看见的薄弱点。同时：打分仍取各分项 **max**（不触发「同一维度被多来源放大」），展示仍取最差来源成对取值（D15 的正确性不受影响）。三处口径互不串用。

**`Math.max(0, …)` 的作用**：脏数据（负数题量）会污染阈值——如果某条来源上报 `totalQuestions = -5`，直接累加会让 `evidenceQuestions` 变小，把合格维度挤回「数据不足」。钳到 0 后，脏来源最多「不贡献证据」，不会倒扣。

**测试侧终态**：`weakness.test.ts` 新增 1 条「阈值按多来源证据量累加判定，不因单来源样本小被埋（裁决 B）」，断言 `ranked.length === 1` / `insufficient` 为空 / 展示仍是 `错 3/6 题` / **不含** `3/12`，并加 4+4 = 8 < 10 的**对照组**证明「累加是为了让分散证据被看见，不是为了降低门槛」。最后两条把「阈值可累加、展示不可累加」这个双字段不变量钉死——只锁前两条的话，将来有人「顺手统一口径」把展示也改成累加，测试抓不到。

**若将来要回退**：这条断言会先红（`ranked.length` 期望 1 实得 0），消息里直接写明「按单来源 6 题判『数据不足』会系统性埋掉分散证据的维度」，可自解释。
