# v2.7 升级与回滚指南（Migration Guide）

> 适用：从 **v2.6** 升级到 **v2.7**（规划内核）。
> 迁移脚本：`scripts/migrations/v2.7.mjs`
> **校验和（checksum）：`8563a351ba6ba475`** —— 脚本会把它登记进 `AppMigration`；同版本不同校验和会被拒绝执行。

> v2.7.1 增量升级见 `docs/v2.7.1-release-checklist.md` §4.1：迁移脚本为 `scripts/migrations/v2.7.1.mjs`，checksum 为 `7cd30baa4974708b6b1d2c3e4d279b45cff71eff1a30e78fceff06a4f58328bb`，只接受显式 `/tmp` 隔离库做演练；真实库当前禁止写命令，事故与回滚门禁未关闭前不得首次使用。

## 0. 先读懂三条边界

| 边界 | 含义 |
|---|---|
| **纯加法** | 只做 `CREATE TABLE` / `ADD COLUMN` / `CREATE INDEX`。**不删列、不改列类型、不删行、不改语义** |
| **幂等** | 重复执行不重复生效（`IF NOT EXISTS` + `PRAGMA table_info` 预检）；同版本不同校验和**拒绝执行**（防脚本被悄悄改动） |
| **无 `down` 脚本** | 回滚 = **恢复备份**（`scripts/restore.sh`）。理由见 §5 |

本次迁移的完整改动量：

| 项 | 数量 | 明细 |
|---|---|---|
| 新建表 | **5** | `PlanningSnapshot` / `SkillGap` / `TaskCandidate` / `TaskPriorityDecision` / `StageReadinessReview` |
| 追加列 | **10** | `LearningCycle` **+3**（`phaseChangedAt` / `primaryTheme` / `secondaryThemesJson`）<br>`PlanTask` **+2**（`candidateId` / `decisionJson`）<br>`PlanVersion` **+5**（`layer` / `parentVersionId` / `snapshotId` / `staleAt` / `staleReason`） |
| 新建索引 | **10** | 新表 8 个 + 被改造表 2 个（`PlanTask_candidateId_idx` / `PlanVersion_snapshotId_idx`） |
| 反向 DDL | **0** | 见 §5 |

> 追加的 10 列**全部可空**，因此对既有行没有默认值回填问题；`prisma db push` 在迁移后应为**零变更**（列顺序按 Prisma 字母序排列，刻意对齐，避免 `db push` 重建带数据的老表）。

## 1. 升级前：必须做一致性备份

```bash
bash scripts/backup.sh
```

**不要用 `cp prisma/dev.db`。** 两条理由（都在 `scripts/backup.sh` 头部写着）：

1. WAL 模式下库由 `dev.db` + `dev.db-wal` + `dev.db-shm` 三者共同构成，已提交但尚未 checkpoint 的事务只在 `-wal` 里 —— `cp` 会**静默丢掉**最近的写入，得到一个「少了若干次写入」甚至打不开的文件；
2. 即便当前是 `journal_mode=delete`，`cp` 也只是逐字节搬运；若复制期间有跨语句事务进行中，可能拿到中间状态。

`backup.sh` 走 SQLite 官方的 `.backup`（按页复制 + 持读锁），产出的是**自洽快照**；失败时自动退化为 `VACUUM INTO`。产物命名 `backups/dev-<时间戳>.db`。

> 迁移脚本会**强制检查**「当天是否已有备份」（期望 `backups/dev-<今日stamp>-*.db`），没有就中止。`--allow-no-backup` 只应用于**副本演练**，不要对真实库使用。

## 2. 预演（dry-run）

```bash
node scripts/migrations/v2.7.mjs --dry-run
```

会打印：将执行的建表/追加列/索引语句、**校验和**、当前库的版本登记情况、受保护表的行数基线。**不写库。**

若想先在副本上完整演练（推荐先做一次）：

```bash

cp backups/dev-<时间戳>.db /tmp/ielts-v27-drill.db
node scripts/migrations/v2.7.mjs --db /tmp/ielts-v27-drill.db --dry-run
node scripts/migrations/v2.7.mjs --db /tmp/ielts-v27-drill.db --allow-no-backup
```

## 3. 正式执行

```bash
node scripts/migrations/v2.7.mjs
```

执行时的三件事（同一个 `BEGIN IMMEDIATE` 事务内完成，失败整体回滚）：

1. DDL：5 建表 + 10 追加列 + 10 索引；
2. **前后核对**：受保护表行数零漂移、被改造表「旧列一个不少 + 新列都在」；
3. 版本登记：`AppMigration` 插入 `('appmig-v2.7', 'v2.7', '8563a351ba6ba475', …)`。

报告写入 `backups/migrations/v2.7-<时间戳>.json`（含 checksum、行数基线、integrity/外键检查结果）。

**前置条件**：库里必须已有 `AppMigration` 表且 `v2.6` 已登记 —— 否则脚本直接中止（`缺少 AppMigration 表` 或 `未找到前一版本`）。

## 4. 迁移后自检（五项，缺一不可）

```bash
DB=prisma/dev.db

# ① 结构完整性
/usr/bin/sqlite3 $DB "PRAGMA integrity_check;"          # 期望：ok
/usr/bin/sqlite3 $DB "PRAGMA foreign_key_check;"        # 期望：无输出

# ② 5 张新表都在
/usr/bin/sqlite3 $DB "SELECT name FROM sqlite_master WHERE type='table' AND name IN ('PlanningSnapshot','SkillGap','TaskCandidate','TaskPriorityDecision','StageReadinessReview') ORDER BY name;"

# ③ 10 个新列都在（逐表计数，期望依次为 3 / 2 / 5）
/usr/bin/sqlite3 $DB "SELECT 'LearningCycle', count(*) FROM pragma_table_info('LearningCycle') WHERE name IN ('phaseChangedAt','primaryTheme','secondaryThemesJson')
UNION ALL SELECT 'PlanTask', count(*) FROM pragma_table_info('PlanTask') WHERE name IN ('candidateId','decisionJson')
UNION ALL SELECT 'PlanVersion', count(*) FROM pragma_table_info('PlanVersion') WHERE name IN ('layer','parentVersionId','snapshotId','staleAt','staleReason');"

# ④ 版本登记与校验和
/usr/bin/sqlite3 $DB "SELECT version, checksum FROM AppMigration WHERE version='v2.7';"
# 期望：v2.7|8563a351ba6ba475

# ⑤ Prisma 结构与库一致（期望：无变更、不重建老表）
npx prisma db push --skip-generate
```

再跑一遍应用自带校验（若存在）：

```bash
bash scripts/verify.sh
```

## 5. 回滚：恢复备份，没有 `down` 脚本

```bash
bash scripts/restore.sh backups/dev-<升级前的时间戳>.db
```

`restore.sh` 的流程（细节见脚本头部）：校验备份自身 `integrity_check` → 读四张关键表行数作基准 → 检查目标库旁是否有 `-wal` / `-shm` / `-journal` 残留（有则中止并给指引）→ 两步交互确认（先 `y`，再输入全大写 `RESTORE`）→ 把当前库另存为 `<db>.before-restore-<时间戳>` → 用 `.backup` 展开备份并自检 → 覆盖后再跑 `integrity_check` 与行数比对。

### 为什么没有 `down` 脚本

| 理由 | 说明 |
|---|---|
| **写反向 DDL 的风险大于收益** | 回滚要 `DROP` 5 张表和 10 个列。SQLite 的 `DROP COLUMN` 在带索引/约束时会重建表 —— 对 `PlanTask` / `PlanVersion` / `LearningCycle` 这三张**带真实数据**的表，重建是这整件事里最不愿发生的情况 |
| **纯加法使「恢复备份」等价于回滚** | 新表与新列不被旧代码读取，所以「不升级」与「升级后回滚」的最终状态一致：都是一份 v2.6 结构的库 |
| **回滚会丢证据** | 单独 `DROP` 新表会丢掉 `PlanningSnapshot` / `TaskPriorityDecision` —— 那是「当时为什么这样排」的唯一记录。恢复备份至少保留「回滚时刻的完整过去」 |

**注意**：回滚 = 丢回滚点之后的所有写入。所以升级前那次 `backup.sh` 是唯一的回滚点，不要跳过。

## 6. 已知遗留（**本次不修**，留 v2.8）

| # | 遗留 | 为什么本次不修 |
|---|---|---|
| 1 | `AIEngineSetting.id` 在 Prisma 上是 `@default("default")`，但 SQLite DDL 里**没有 `DEFAULT` 子句**（`"id" TEXT NOT NULL PRIMARY KEY`）。裸 SQL 插入不带 `id` 会失败；Prisma 客户端会补，所以应用侧无感 | v2.4 旧账（`docs/25-v2.4.1-test-report.md` 已记）。修它要重建表或加触发器，会破「纯加法」边界 |
| 2 | v2.5 语音域 **9 张表**（`AudioAsset` / `Transcript` / `TranscriptSegment` / `ListeningExercise` / `ListeningAttempt` / `ListeningError` / `SpeakingPrompt` / `SpeakingSession` / `SpeakingTurn`）在 SQLite DDL 中**没有任何 `ON DELETE` 子句**（实测 `sqlite_master.sql` 里 `ON DELETE` 命中 0），删父行会留下孤儿 | 加级联外键必须重建这 9 张表；本次迁移的边界是「不碰既有表结构」 |

两条都不影响 v2.7 功能，但会影响「删数据时的连带行为」，所以在升级须知里显式列出。

## 7. 从 v2.6 升级：可直接复制的命令序列

```bash
# 0) 确认当前库状态与版本
/usr/bin/sqlite3 prisma/dev.db "SELECT version, checksum, note FROM AppMigration ORDER BY version;"

# 1) 一致性备份（禁止 cp）
bash scripts/backup.sh

# 2) 副本演练（强烈建议，尤其第一次）
cp backups/dev-<时间戳>.db /tmp/ielts-v27-drill.db
node scripts/migrations/v2.7.mjs --db /tmp/ielts-v27-drill.db --dry-run
node scripts/migrations/v2.7.mjs --db /tmp/ielts-v27-drill.db --allow-no-backup

# 3) 真实库预演
node scripts/migrations/v2.7.mjs --dry-run

# 4) 正式执行
node scripts/migrations/v2.7.mjs

# 5) 自检
/usr/bin/sqlite3 prisma/dev.db "PRAGMA integrity_check;"
/usr/bin/sqlite3 prisma/dev.db "PRAGMA foreign_key_check;"
/usr/bin/sqlite3 prisma/dev.db "SELECT version, checksum FROM AppMigration WHERE version='v2.7';"
npx prisma db push --skip-generate

# 6) 若第 5 步任一项不符合预期 → 立即回滚
# bash scripts/restore.sh backups/dev-<升级前的时间戳>.db
```

**预期结果**：`integrity_check=ok`、`foreign_key_check` 无输出、`AppMigration` 出现 `v2.7|8563a351ba6ba475`、`prisma db push` 报告无变更。

## 8. 常见问题

| 问题 | 原因与处理 |
|---|---|
| 报「升级真实库前必须先做当日备份」 | 今天还没跑 `bash scripts/backup.sh`。先备份；**不要**对真实库加 `--allow-no-backup` |
| 报「缺少 AppMigration 表」 | 目标库没跑过 v2.4 及之后的迁移。请先补历史迁移，不要手建表 |
| 报「版本 v2.7 已登记但校验和不一致」 | 库里的登记来自**另一个版本的脚本**。禁止直接重跑覆盖；先确认脚本来源，必要时用备份回滚 |
| 报「检测到 PlanningSnapshot 表已存在但 AppMigration 无 v2.7 记录」 | 结构来源不明（手建过表？）。先核对结构来源再决定，不要盲跑 |
| 重复执行迁移 | 安全（幂等）。会再次核对结构并输出报告，不会重复建列/建表 |
| `prisma db push` 提示要重建表 | 说明迁移后的列顺序/类型与 schema 不一致。**不要接受**（会重建带数据的老表）；先比对 `pragma_table_info` 与 schema，把差异报回来 |
