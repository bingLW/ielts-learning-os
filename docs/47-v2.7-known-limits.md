# v2.7 已知限制（Known Limits）

> 承接 `40-v2.7-decisions.md` / `41-v2.7-architecture.md`。每条都必须回答两件事：

## 1. 候选采集（T03）

| 能力 | 状态 | 用户会看到什么 |
| --- | --- | --- |
| `OPEN_TASK`（写作）的默认时长 | **20 分钟是粗估** | 一篇 40 分钟级的大作文仍会被排在很后面。skill 覆写**改善但不解决**准确性：它只把「看起来放得下 15 分钟」改成「看起来放得下 20 分钟」，没有做真实的写作时长预测。若某天用户抱怨「大作文总排不上」，先查这里，不要先去调权重 |
| `OPEN_TASK`（口语）的默认时长 | **10 分钟是粗估** | 与写作同理。`IELTS_PART` 的整段模考（11–14 分钟含追问）会被当成一次 10 分钟任务 |

### 1.1 采集层的三处已知偏差

这三条是**实现与 `41 §2.3.2` 的差异**，不是缺陷，但必须写下来：

| # | 差异 | 为什么不按规格做 | 后果 |
| --- | --- | --- | --- |
| 1 | `QUESTION` 来源的前置条件**留空**（规格写 `{STAGE_AT_LEAST}`） | 全仓没有「技能 → 最低阶段」的真值表（`STAGE_META` 只有 `allowedEgiu`）。凭空补一张表会在 S0/S1 静默挡掉**全部**题库候选，而"候选池突然空了"没人能归因 | 低阶段也会看到高阶段题型的候选；由评分层的 `goalRelevance` / `preferenceFit` 压低，而不是硬挡 |
| 2 | `SpeakingPrompt` **不过滤 `active`** | Phase A 没给这张表加 `active` 列（`41 §2.3.2` 的"新增默认 true"未落地） | 已停用的口语题仍会进候选池；下个版本补列后需同时补 `where` |
| 3 | `ReviewTask(targetType='MISTAKE')` 落到 `P0_REVIEW` / `META` | `Mistake` 表没有 `skill` 列（只有 `knowledgePoint` / `errorCategory`），行上读不出这是哪一科 | 错题复习的时间进 `META` 桶、**不**进四技能分母。硬猜一科会把阅读错题记成写作训练时间，比不记更糟 |

## 3. 评分层（T04）

| 能力 | 状态 | 用户会看到什么 |
| --- | --- | --- |
| `errorRecurrence`（同类错误重复度） | **`0.00` 只在「该维度确实练过」时才等价于「没有重复错误」** | 若 28 天内该维度**一次都没练**，那是「没有观察」而不是「没有错误」。当前口径**仍返回 `0.00`**（错误重复度是**加重因子**而不是发现因子，未观察的维度应由 `PROBE` 补测路径接手，而不是靠这个因子被抬升），但 `/planner/candidates` 的决策轨迹会显式显示「近 28 天无记录（未观察）」而不是「0 次错误」。区分方式：`factorsJson.meta.noObservation` |
| `preferenceFit`（偏好匹配） | **默认 `0.50` 是「不知道偏好」，不是「中等喜欢」** | 用户没表达过偏好时该因子恒 0.50，界面上必须标成「无偏好数据」。若将来把它显示成一个"评分"，用户会以为系统对他的偏好有判断 |
| `goalRelevance`（目标相关度） | 只在**有在跑的 90 天周期 + 有目标日**时才算得出 | 没有周期时该因子恒 `0.50`（中性），所以此时"目标相关度"并不参与区分候选，排序主要由到期压力与证据支撑决定 |

> 若后续能稳定拿到「该维度是否练过」的信号（`SkillGapSignal.evidenceQuestions > 0` 已可判），可把「未观察」升级为中性 `0.30`。这属于**口径变更**，必须递增 `weightsVersion`，否则历史决策不可复算。

### 3.1 `repeatedErrorCount`（错误重复次数）的口径

它是 `Mistake` 表近 28 天里**能归属到 `StudyRecord` 的错题条数**（技能从
`StudyRecord.skill` 取）。三点必须知道：

| 限制 | 后果 |
| --- | --- |
| `studyRecordId` 为空的错题不计入 | 手工录入、没挂学习记录的错题不会提高 `errorRecurrence`。宁可漏计也不错挂到某个技能上。**这是「按 `studyRecord.recordDate` 过滤窗口」的自然结果，不需要额外写一个 `studyRecordId: { not: null }`** —— 多写一个条件就多一处可以忘、也可以写错的地方 |
| 统计窗口按 `asOfDate` 回推 28 天，不是按「现在」 | 这是为了让同一 `asOfDate` 的快照永远可复算（否则同一输入在不同时刻算出不同 `inputHash`） |
| **窗口按错题「发生」的日期算，不是按「录入」的日期** | 这两个锚点会分叉：用录入时刻（`Mistake.createdAt`）的话，补录半年前的错题会让今天的 `repeatedErrorCount` 突然升高，而那些错题对历史 `asOfDate` 又永远不可见。所以锚点是 `StudyRecord.recordDate`（业务日期）。**补录不改变过去发生了什么，只改变「当时那些错确实存在」这件事被记录下来了** —— 只有按 `recordDate` 算，补录才会正确地落进它该落的窗口 |

## 4. 数据层遗留（**休眠风险**，不是当前缺陷）

这两条**今天不产生错误结果**，因为没有任何代码会触发它们；但将来谁加了相应功能就会撞上。所以按「休眠风险」记录，而不是按缺陷。

| 遗留 | 现状 | 触发条件（将来什么时候会疼） |
| --- | --- | --- |
| v2.5 语音域 **9 张表**没有级联外键 | `AudioAsset` / `Transcript` / `TranscriptSegment` / `ListeningExercise` / `ListeningAttempt` / `ListeningError` / `SpeakingPrompt` / `SpeakingSession` / `SpeakingTurn` 在 SQLite DDL 中**没有任何 `ON DELETE` 子句**（实测 `sqlite_master.sql` 里 `ON DELETE` 命中 0），Prisma schema 侧同样无 `onDelete: Cascade` | 目前**没有任何代码删除这些父表行**，所以不产生孤儿行。一旦有人加「删除音频资产 / 删除听力练习 / 清理会话」这类功能，子表（转写、分段、尝试、会话、轮次）会留下指向已删父行的孤儿记录 —— 而 SQLite 默认不报错，页面只会显示「内容已移除」之外的怪状态。修它必须重建表，**不在 v2.7 的纯加法边界内**，留 v2.8 |
| `AIEngineSetting.id` 缺 DDL 级 `DEFAULT` | Prisma 上是 `@default("default")`，但 SQLite 里是 `"id" TEXT NOT NULL PRIMARY KEY`（无 `DEFAULT`）。Prisma 客户端插入时会补 `id`，所以应用侧无感 | 只有在**绕过 Prisma** 写裸 SQL / 数据修复脚本 / 手工 `INSERT` 时才会失败（`NOT NULL constraint failed`）。修它要重建表或加触发器，同样破纯加法边界，留 v2.8 |

> 判断「休眠风险」还是「缺陷」的判据：**有没有代码路径能触发它**。有 → 缺陷，本版修；没有 → 休眠风险，记录 + 等触发它的功能一起做。

## 5. 计划解释（T07）

| 能力 | 状态 | 用户/维护者会看到什么 |
| --- | --- | --- |
| 解释的「有据可查」边界 | **`buildPlan` 的 `explanation.reason` 取自同一次调用的内存决策（`context.decisions`），从不回读已落库的 `TaskPriorityDecision.rationale`** | 只要「评分是确定性的」成立，内存决策与落库决策一致，用户看到的就是有据可查的；但 §4.4 的「篡改落库 decision → 重读解释 → reason 跟着变」这个反证**当前会失败**（重新 `buildPlan` 会现算，仍给原文案）。独立「读解释」路径是 T10 查询层（`getPlanExplanation`）的职责，届时必须回读 `PlanTask.decisionJson` / `TaskPriorityDecision.rationale`，而不是重新 `scoreCandidate`。在此之前不把「篡改落库 decision 会回溯」当作承诺 |

## 6. 重排与 carryover（T08）

| 能力 | 状态 | 用户/维护者会看到什么 |
| --- | --- | --- |
| `confirmReplan` 幂等闸门的并发语义 | **并发双提交会穿透 token 闸门与 PRECONDITION 闸门，在事务内触发 `idempotencyKey` 的 `@unique` P2002 异常，而非优雅 `fail('CONFLICT')`** | SQLite 单连接（`connection_limit=1`）下概率极低。若将来调大连接池或引入多写并发，重复提交会抛 500 而非被幂等闸门礼貌拦截。幂等闸门本身的「重复 key → CONFLICT」拦截逻辑已补专测，但「双提交走 P2002」这条异常路径未做优雅化（catch P2002 → 转 CONFLICT），留作后续加固 |
| `carryoverApply` 尚未接线 | **挂载点已裁决：生成新一天计划流程（T07 `buildPlan` 的 GENERATE 路径），不是 replan**。`applyCarryover` / `carryoverPolicy` 当前全仓无非测试调用点，编排待「carryover 日滚存」小任务落地（依赖 T07+T08） | 用户现在**用不到** carryover。接线时：preview（`generatePlanPreviewAction`）内存调 `carryoverPolicy` 不落库、confirm（`confirmPlanVersionAction`）同一事务先 `applyCarryover` 再写今日任务；`previewTokenOf` 须补 `carryoverOverdueFingerprint`（每条 overdue 的 `taskId:planDate:priority:movedCount:splittable:plannedMinutes:actualMinutes:minChunkMinutes`）。replan 的 `notStarted` 过滤（`status==='TODO' && actualMinutes<=0`）会把**已滚入今天**的产物再 DEFER，故 replan 必须把滚入产物作为 `lockedTaskIds` 保护——这是「replan 保护已滚入任务」，不构成「carryover 由 replan 触发」 |
| `previewToken` 不含 `timerStatus` | **指纹精确符合 PRD §2.7（status / actualMinutes / plannedMinutes / planVersion 均已入签），但不含前端计时器运行态 `timerStatus`** | 窄场景：IN_PROGRESS 任务在暂停态（timerStatus=IDLE）预览到 SHRINK → 用户恢复计时（IDLE→RUNNING，status 仍 IN_PROGRESS、actualMinutes 未变）→ confirm 不 CONFLICT，却按 KEEP(冻结) 而非预览的 SHRINK 落库，即「预览≠实际」。TODO 任务不受影响（`startTimer` 会改 status 入签）。`timerStatus` 是前端运行态、不一定落库，若将来要纳入指纹需先解决其服务端可见性 |

## 7. 阶段就绪度（T09）

| 能力 | 状态 | 用户/维护者会看到什么 |
| --- | --- | --- |
| D1 覆盖率依赖 `SkillGap.coverageRatio` | **当前 `buildPlanningSnapshot` 装配缺口时 `coverageRatio` 恒为 `null`（真实值需要分题型正确率，证据行尚无该维度）** | 服务层产出的 D1 会偏保守：`null` 按「覆盖未知 → 未达标」处理，真实 readiness 结论几乎到不了 `READY_FOR_REVIEW`。这不影响 `computeReadiness` 纯函数（单测用手抄输入覆盖了 D1 全 PASS 分支）；`coverageRatio` 的真值接入属于后续数据装配工作 |
| D2「方向一致」的判定口径 | **`SkillGapDraft` 没有显式「方向」字段**，`computeReadiness` 用 `coverageRatio` 二分：`< READINESS_COVERAGE_MIN`（或 null）=「覆盖型缺口」、`≥` =「严重型缺口」；同一技能同时出现两种方向才判 FAIL | 在当前数据（`coverageRatio` 恒 null）下所有缺口同向，D2 方向检查不会 FAIL。这是对「各来源方向一致（gap 方向相同）」的**可执行近似**，若架构师认为「方向」应取别的信号（如 `accuracyDelta` 的正负），需回到 `SkillGapDraft` 补字段并改 `gapDirection()` |
| `confirmStageTransitionAction` 不切阶段状态 | **只写 `StageReadinessReview.outcome=USER_APPROVED_TRANSITION` + `userConfirmed` + `StageTransitionLog`，不改 `Stage.status`** | 真正切阶段仍走既有 `transitionStageAction`（`actions/stages.ts`）。两个 action 都在 `StageTransitionLog` 留痕，但职责不同：一个是「批准证据结论」，一个是「改阶段状态」。若产品要求「确认进入下一阶段」一次性完成状态切换，需在此 action 里补 stage 状态翻转（复用 `transitionStageAction` 的事务语义） |
